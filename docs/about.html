What is this, exactly?

No jargon, no register maps — just what's being built, why it's being built the hard way, and what happens next. If you want the technical build log with live progress instead, it's over here.

The short version

This is a small electronic device — smaller than a deck of cards — built to sense its surroundings (things like temperature, distance, air pressure) and send that information over Wi-Fi, the same way a smart thermostat or a fitness tracker does. What makes it different is how it's built: every single instruction it runs was written by hand, at the lowest level a computer chip understands, instead of using the pre-made software toolkits most projects rely on.

Think of it like the difference between assembling furniture from a kit with an instruction booklet, versus milling the wood and cutting the joints yourself. Both end in a table. Only one teaches you how a table actually works.

Two chips, two jobs

the device has two small computers on it, not one

chip 1

STM32 — the hands

This chip is wired directly to the sensors and does the moment-to-moment work: reading a temperature sensor, timing a distance pulse, driving a small display. It's fast, cheap, and has no operating system — every task it does is a sequence of instructions written specifically for it.

chip 2

ESP32 — the mouth

This chip has Wi-Fi built in. It doesn't touch the sensors directly — instead, the STM32 hands it readings over a wire, and the ESP32's only job is getting that information onto the internet, and later, delivering software updates back down.

Splitting the work this way mirrors how real embedded products are designed: one chip focused on hard real-time control, one focused on connectivity, talking to each other over a simple, reliable wire — not two jobs bolted onto one chip that's mediocre at both.

Why not just use Arduino?

Arduino (and similar tools) exist to hide complexity — you write a few lines of code, and a huge stack of pre-written software handles the messy details of talking to the actual hardware underneath. That's genuinely useful for building things quickly.

This project deliberately skips that stack. Every peripheral — the pins, the communication ports, the clock that keeps the chip's timing accurate — is controlled by writing directly into the chip's hardware "switches" (called registers), guided only by the manufacturer's official documentation. It's slower to build, and mistakes are easier to make. In exchange, there's no mystery layer between the code and the silicon — which is exactly the point: this project exists to build that understanding from the ground up, not just to end up with a working gadget.

Common questions

What's a microcontroller?

A tiny, self-contained computer on a single chip — a processor, some memory, and the wiring to control other hardware, all in one package. It's what runs inside a microwave, a car's dashboard, or a smart thermostat. No screen, no operating system, no mouse — it just runs one program, forever, until it's powered off.

What does "register-level" or "bare metal" mean?

A chip's hardware features are controlled through specific memory addresses called registers — flipping a particular bit at a particular address might turn on a pin, or start a timer. "Register-level" or "bare metal" programming means controlling the chip directly this way, rather than through a software library that does it for you.

Is this basically an Arduino project?

It runs on similar chips, but it doesn't use the Arduino software or its libraries. Everything — startup code, the compiler settings, the memory layout, every driver — is written and controlled directly, which is the entire point of the project.

What's OTA?

Short for "over-the-air" — updating a device's software wirelessly instead of plugging it into a computer. It's how a phone or a smart speaker gets new software. Building this for a bare-metal device is a genuinely hard, industry-relevant problem, which is why it's a planned phase here.

Why not just buy a smart sensor instead of building one?

Because the point isn't the sensor readings — it's understanding, first-hand, everything a commercial smart device is quietly doing underneath: clock configuration, interrupt handling, communication protocols, safe firmware updates. The finished device is a side effect of that learning process.

No HAL. No Arduino framework. Documented as it's built.
